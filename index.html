01 · The part that matters most

Seven decisions the brief leaves unmade

Headline plus resolution is the whole argument. Expand only if you want the code.

1
Amazon is listed under both flow modelscontradiction → Read as order-dependent, not sloppy. Single-seller single-shipment batches; split shipment goes sequential.
+
"Batch flow (e.g. Amazon)..." / "Sequential flow (e.g. Amazon, Flipkart)..." Brief, §2

Most consequential line in the document: the wrong answer means skipped items or duplicate filings.

def _amazon_flow_model(items) -> FlowModel:
    sellers   = {i.get("seller_id")   for i in items if i.get("seller_id")}
    shipments = {i.get("shipment_id") for i in items if i.get("shipment_id")}
    return FlowModel.BATCH if len(sellers) <= 1 and len(shipments) <= 1 else FlowModel.SEQUENTIAL

Unknown platforms default to sequential: over-processing is recoverable, silent skipping is not.

2
Re-run safety: absent from the brief, and the costliest failure heremissing → Idempotent by construction. Only To Do / In Progress rows load; every item commits to disk the moment it resolves.
+

The brief assumes the loop finishes. In production it dies at item 30 of 50 and someone re-runs it. A naive implementation re-files returns it already filed. Duplicate returns create support tickets, can trip fraud review, and are worse than no automation.

# load_pending_tasks: rows already terminal are never re-read
if status not in (None, "", TaskStatus.TO_DO.value, TaskStatus.IN_PROGRESS.value):
    continue

A crash costs nothing already done, and re-running becomes the safe default rather than something an operator has to think hard about first.

3
Bot avoidance is mandatory in §1 and a bonus in §6contradiction → Built it properly, but reframed the goal to reducing detection risk. Nobody can guarantee the mandatory version.
+
"...must run without getting flagged or blocked as a bot" (§1) vs "6. Bot-Detection Avoidance (Bonus)"Brief, §1 and §6

No client-side technique reliably defeats server-side detection. Anyone claiming they solved it is overstating. Five signal categories covered, headful not headless:

  • Fingerprint: patch navigator.webdriver, plugins, languages
  • Timing: delays sampled from a distribution, never a fixed sleep
  • Motion: randomised cursor path to target instead of teleporting
  • Input: per-character typing with jitter, not fill()
  • Session: persistent profile dir, so the account reads as a returning user
4
Out of window: is the task Done, or does a human review it?undefined → Done. The agent reached a correct final answer. Routing it to review floods the queue with items needing no decision.
+
"Return status: Placed / Failed / Out of window" · "Task status: Done / Needs human review"Brief, §4

Two vocabularies, no mapping between them. Failed maps to review, where human judgment actually adds something.

self.task_status = (
    TaskStatus.DONE if return_status in (ReturnStatus.PLACED, ReturnStatus.OUT_OF_WINDOW)
    else TaskStatus.NEEDS_REVIEW)

If your ops team chases out-of-window items for goodwill refunds, my default is wrong and it's a one-line change. That's a question about your process, which is why I've surfaced it.

5
"Return window: Input / verified". Who wins when Excel and the platform disagree?undefined → Excel is a cheap pre-filter, the platform is truth. A missing window means ask the platform, never assume ineligible.
+

Eligibility is checked before a browser opens, so hopeless items cost nothing and don't add avoidable traffic to an account we want unflagged. The adapter checks again live; the platform wins.

def is_eligible(self, as_of=None) -> bool:
    as_of = as_of or date.today()
    if self.return_window_end is None:
        return True  # unknown window: let the platform judge
    return as_of <= self.return_window_end

Assuming ineligible on missing data would be a silent revenue leak. Systematic disagreement between sheet and platform is also an upstream data-quality signal worth reporting.

6
§5 wants an order-level status that §4's schema can't storeinconsistency → Derived, never stored. Two sources of truth drift; a derived property is correct by definition.
+
"Only mark the order fully Done when every line item has a final recorded state." Brief, §5
@property
def is_fully_done(self) -> bool:
    return all(t.task_status in (TaskStatus.DONE, TaskStatus.NEEDS_REVIEW) for t in self.tasks)

Surfaced in the audit log's per-order summary, so a human sees it without a column the spec never defined.

7
"Failed" bundles two failures needing opposite treatmentundefined → Out of window never retries. Timeouts retry 3× with backoff plus jitter. Conflating them breaks one or the other.
+
FailureRetryCost of getting it wrong
Out of windowNever Wastes time, fires repeat requests at an account we want unflagged, never succeeds.
Timeout, selector miss3× backoff Giving up turns a routine blip into a false "needs review". A human handles what attempt two would have fixed, defeating the point of automating.
backoff = BASE_BACKOFF_SECONDS * (2 ** (attempt - 1)) + random.uniform(0, 1)

Jitter is deliberate: fixed backoff across a batch produces synchronised retry bursts, itself a bot signal.

Why this section leads

Writing the code was the smaller half. Deciding what it should do where the brief was silent is the half that looks like the job. Each of the seven is somewhere a reasonable person could have built something different and never mentioned it.

03 · Architecture

How it fits together

Click a component

The structural choice: Amazon and Flipkart share nothing at the DOM level, and retail markup changes constantly. Platform fragility is confined to one file per platform behind a shared interface. The orchestrator has no if platform == branch anywhere, so adding Myntra is one new file, not edits to shared control flow.

04 · Judgment

Flow detection is a rule, not an LLM call

The obvious approach, and the one in a publicly posted solution to this same brief, is to have an LLM read the page and infer the flow. I didn't.

LLM inferenceDeterministic rule
Wrong howRarely, but unpredictablyPossibly more often, identically every time
DebugSampled at inference, may not reproduceRead one dict, know the behaviour
TestNeeds mocks, still non-deterministicFive plain unit tests
CostTokens plus a round-trip per orderZero
FailureMisclassify batch as sequential → duplicate return filed, invisible until support hears about it Falls back to sequential: over-processes, never double-files

That last row is the argument. Flow model is a property of the platform's UI, not something that should vary run to run. What I give up: my rule won't cover a platform I haven't seen, where an LLM degrades more gracefully. Unknown platforms default to sequential, and each new case becomes a permanent rule plus a test rather than a hope the next inference goes better.

Selectors in YAML, not Python

DOM drift is the most likely cause of a bad run. In config, a break is a one-line edit an ops person makes, not a code change plus review plus redeploy. That's the difference between a tool that survives production and one quietly abandoned after the third break.

Demo mode exists for your time, not mine

I could have shipped code that only runs with a live Flipkart login. --demo exercises the same orchestration, eligibility, retry and write-back paths with no browser, so this is reviewable in two minutes without provisioning anything.

06 · Scope

What's real, what isn't, what's next

Working and tested

  • Excel read/write, all ten spec fields
  • Order grouping, independent per-item processing
  • Eligibility check before any browser session
  • Partial success, verified against the brief's example
  • Batch vs sequential across five cases
  • Retry with exponential backoff plus jitter
  • Idempotent, resumable after a crash
  • Structured audit logging

Scaffolded, needs a live session

  • The CSS selectors. Written against typical returns-page structure, not verified live, because Flipkart login needs an OTP by phone call.
  • Stealth measures are wired in, but live durability is empirical and untested.
  • The OTP step is inherently human. I built the seam (_await_human_otp_entry) rather than faking a workaround.

Every candidate without a working test account is in this position. The difference is whether they say so.

First two weeks with real usage

NextEffortWhy first
Selector health check½ day Confirms every selector resolves before a batch. Turns "50 orders failed overnight" into one alert before we start. DOM drift is the likeliest cause of a bad run.
Recovery-rate dashboard½ day Refund value recovered, success rate by platform, review-queue age. Nobody reads JSONL daily. Turns a script into something with an owner and a number.
Sheet-vs-platform drift report1 day From gap 5. Systematically stale windows are an upstream process problem worth more than any individual return, and this agent is the only thing positioned to see it.
Volume-aware rate limiting1 day A new low-activity account filing 50 returns in an hour is a different risk profile from an established one. Per-action delay doesn't capture that.

What I'd ask before writing production code

  • Does ops chase out-of-window items for goodwill refunds? Changes gap 4's default.
  • What daily volume, across how many platform accounts? Sets whether rate limiting is week one or month three.
  • Who works the review queue, and what's the SLA? An unworked queue means the work moved rather than disappeared.
  • Is Excel the long-term interface or a stopgap? Changes how much to invest there versus abstracting behind a repository.
